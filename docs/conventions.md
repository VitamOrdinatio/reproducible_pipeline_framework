# Pipeline Conventions  
## reproducible_pipeline_framework v2

---

## Purpose

This document defines conventions used throughout this repository to support:

- reproducibility
- readability
- consistent structure
- clean execution
- easy extension
- transparent data flow

These conventions apply to:

- pipeline stage modules
- configuration
- artifact organization
- logging
- documentation
- testing

---

## Repository Layout Conventions

### config/
Contains configuration files that control pipeline behavior.

- `config.yaml` defines execution mode, thresholds, and key parameters.

---

### data/
Contains input and intermediate data.

- `data/example/` — small toy datasets for example runs
- `data/raw/` — raw input data (not modified)
- `data/interim/` — intermediate artifacts generated during pipeline execution
- `data/processed/` — cleaned or enriched data ready for downstream analysis

---

### pipeline/
Contains executable stage modules.

- Each stage is implemented as a standalone Python module.
- Each stage exposes a `run_stage()` function.
- Stage filenames follow the convention:

```
stage_XX_<description>.py
```

Example:

```
stage_01_load_data.py
stage_02_align_data.py
...
stage_13_write_summary.py
```

---

### src/
Contains reusable internal code:

- pipeline orchestration
- configuration loading
- path management
- logging utilities
- metadata helpers

Code here should be:

- reusable
- side-effect minimal
- independent of specific stages

---

### results/
Contains all outputs generated by pipeline runs.

```
results/
  runs/
    <run_id>/
      final/
      validation/
      reports/
      logs/
      metadata.json
```

Each run is self-contained and auditable.

---

### docs/
Contains documentation describing:

- pipeline behavior
- architecture
- data schemas
- state contracts
- conventions
- design rationale

---

### tests/
Contains:

- integration tests
- validation scripts
- test scaffolding

---

## Stage Naming Conventions

Stages are:

- numbered sequentially
- named descriptively
- prefixed with `stage_XX_`

This ensures:

- clear execution order
- predictable orchestration
- easy debugging

---

## Logging Conventions

Each stage must log:

- start and completion
- key input files
- key output files
- record counts where applicable
- warnings and errors

Logs are written to:

```
results/runs/<run_id>/logs/pipeline.log
```

---

## State Management Conventions

The shared `state` object:

- is passed explicitly to each stage
- stores paths to artifacts (not large objects)
- records QC metrics
- records warnings and errors
- supports reproducibility and auditability

State structure is formally defined in:

```
docs/state_contract_v2.md
```

---

## Configuration Philosophy

Pipelines must not hardcode:

- file paths
- thresholds
- reference genome paths
- filtering parameters

Instead, these must be defined in:

```
config/config.yaml
```

This enables:

- reproducibility
- portability
- easy experimentation

---

## Reproducibility Principles

This framework aims to ensure that:

- pipelines are rerunnable from the same inputs
- outputs are deterministic for toy data
- intermediate artifacts are preserved
- no hidden manual steps exist inside the pipeline

Manual review steps (e.g., IGV inspection) must be clearly documented as external to automation.

---

## Documentation Expectations

Every pipeline built using this framework should include:

- a README
- a documented state contract
- a data schema
- clear workflow documentation
- explicit assumptions and limitations
